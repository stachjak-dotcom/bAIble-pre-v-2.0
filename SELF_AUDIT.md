# Self-Audit

Use this checklist when improving or publishing bAIble.

## Purpose and usability
- [ ] Purpose and scope are clear.
- [ ] A complete beginner can start with the public repository.
- [ ] The first steps are understandable without private context.
- [ ] Core principles are distinguishable from examples.
- [ ] Technical terms are explained before they become necessary.
- [ ] The guide can be useful without adopting every optional concept.

## Collaboration
- [ ] Important facts, assumptions, hypotheses, decisions, and unknowns can be distinguished.
- [ ] The AI is not treated as an oracle.
- [ ] Evidence and verification are encouraged where they matter.
- [ ] Human authority and decisions remain visible.
- [ ] Important knowledge can be preserved outside temporary chat context.
- [ ] Handoffs can preserve enough context to continue safely.

## Privacy
- [ ] The public/private boundary is clear.
- [ ] New users are shown where project-specific information belongs before substantial private information is collected.
- [ ] Secrets and confidential information are excluded.
- [ ] No private project depends on being able to understand or access this repository.

## Reality Check
- [ ] Reality Check has a clear purpose.
- [ ] Important conclusions can be challenged against evidence.
- [ ] Unknowns and limitations remain visible.
- [ ] Verification is distinguishable from an AI's self-report.

## Growing the system
- [ ] Optional architecture is introduced only when a real need appears.
- [ ] Governance, context, orchestration, execution, monitoring, and verification remain distinguishable.
- [ ] No concept is presented as mandatory software when it is only a framework idea.
- [ ] The smallest useful setup remains possible.

## Public readiness
- [ ] Links and referenced files exist.
- [ ] Examples match current principles.
- [ ] Claims about implementation are supported by accessible evidence.
- [ ] Generalized lessons do not expose their private origin.
- [ ] A repository-tree/privacy review found no project-specific identifiers, private run IDs, internal paths, credentials, or other sensitive material.

A failed item is a reason to investigate and improve the guide, not automatically proof that the underlying idea is wrong.
