# Self-Audit

Use this checklist before treating a public bAIble revision as complete.

## Contract
- [ ] Purpose and scope are explicit.
- [ ] A complete beginner can start with only the public repository link.
- [ ] The agent establishes a private workspace before collecting substantial project data.
- [ ] The agent establishes or identifies a private project source of truth.
- [ ] Information routing between public and private locations is explicit.
- [ ] Terminology is understandable without private context.
- [ ] Core rules are distinguishable from examples.
- [ ] No private dependency is required.

## Evidence
- [ ] Important claims have appropriate status.
- [ ] Important claims have provenance or are clearly identified as framework principles.
- [ ] Facts, inferences, hypotheses, and unknowns are separated.
- [ ] Verification is distinguishable from agent self-report.

## Reality Check
- [ ] RC triggers are defined.
- [ ] RC has a minimal record.
- [ ] Outcomes and failure/escalation behavior are defined.
- [ ] Authority and approval are visible.

## Bootstrap
- [ ] A fresh participant can create or identify a private workspace.
- [ ] A fresh participant can create or identify a private project repository when needed.
- [ ] A fresh participant knows what belongs in each destination.
- [ ] A bounded task can be run without inventing core governance.
- [ ] Handoff and verification can be recorded.
- [ ] Material project rules have an explicit decision record.
- [ ] The Bootstrap Acceptance Test checks privacy and repository destination.
- [ ] Workspace templates are clearly intended to be copied into the user's private environment.

## Architecture
- [ ] Layers are optional and justified by need.
- [ ] Governance, orchestration, execution/integration, context, monitoring, and verification remain distinct.
- [ ] No component is presented as mandatory software when it is only a concept.
- [ ] Public bAIble contains construction principles, not another project's runtime implementation.

## Security
- [ ] Secrets and private information are excluded.
- [ ] Access and authority are not confused with UI visibility.
- [ ] Destructive actions require appropriate approval.
- [ ] Examples do not expose private implementation details.
- [ ] Public material can be understood without inaccessible private evidence.

## Public-readiness
- [ ] Links and referenced files exist.
- [ ] Examples match current rules.
- [ ] No claim of implementation is made where only a design exists.
- [ ] Uncertainty and limitations are visible.
- [ ] A repository-tree/privacy scan found no project-specific identifiers, private run IDs, internal paths, or secret-like material.

A failed item is a signal to investigate, not automatically proof that the framework is invalid.
